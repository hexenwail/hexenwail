Compiled Hexen II and Portals of Praevus gamecode ships in both zips and loads automatically — see **Compiled gamecode** below for what that means and how to opt out.

### Changes from [0.8.0-beta.r15](https://github.com/hexenwail/hexenwail/releases/tag/0.8.0-beta.r15)

- Fixed the game world running at 20 Hz instead of 72, which slowed anything whose timing is counted in server ticks rather than seconds. Spiders and other monsters attacked at a visibly lower cadence, mod code scheduled to run every frame ran a third as often, and strafe jumping bled speed instead of building it. The engine had been taking its physics rate from `sys_ticrate`, whose 0.05 default is a dedicated-server setting that was never meant to reach the client (reported by BloodShot, with side-by-side video)
  - Added `sv_physfps` cvar (default: 72), the rate the world thinks at, saved to your config. 72 matches what Hexen II has always run at on a machine that could reach it
  - Changed `sys_ticrate` back to affecting only dedicated servers. **If you set it as a workaround, remove it from your config** — it no longer does anything on the client, and leaving it in will confuse your own testing
  - Improved on the original behaviour while there: the tick no longer follows your framerate, so a 60 Hz or 30 Hz display gives the same air control as a 144 Hz one. Vanilla tied the two together
- Fixed `Host_Error: CL_ParseServerMessage: Illegible server message` on busy maps. When more than 255 entities left view in a single tick the server wrote a count that could not describe how much it had sent, and the client resumed reading in the middle of the data. Over-cap removals are now deferred to the next message rather than dropped, so nothing is left behind as a ghost
- Fixed two-state props morphing between their states instead of switching. An upright barrel and a knocked-over barrel are not two frames of an animation; the check that decides which models may be interpolated measured nothing on such models and read that as "perfectly smooth". Verified against 970 models across the base game, Shadows of Turmoil and Wheel of Karma — exactly `barrel.mdl` and SoT's `stalactite_ice2.mdl` change, and every model r15 restored interpolation to keeps it
- Fixed `misc_modelpimp` producing a glow orb nobody asked for. Supplying a `glow_color` for an entity's cast light was being read as a request for the orb as well, contradicting the documentation, where spawnflag **4** grants it. Entities written against the r15 spawnflags now get the documented behaviour; older content keeps the old inference, so none of the 151 `misc_modelpimp` entities in the shipped mods change (reported by Mathuzzz)
- Fixed spawnflag **64** (no dynamic light) being ignored on four of the six lighting effects that can produce one — `EF_BRIGHTLIGHT`, `EF_DIMLIGHT`, `EF_DARKLIGHT` and `EF_LIGHT`. Muzzle flashes stay lit on purpose: they belong to firing rather than to the model, and already have their own switch in `gl_missile_glows`
- Added `r_dlight_model_list` cvar (default: empty), letting a mod name its own models as torches so they cast light like the built-in ones. The light-casting set was hardcoded to Raven's six torch and flame models, which cannot describe a fixture assembled from several models. Comma-separated whole model names, read at model load, so set it from `autoexec.cfg` before a map loads. Built-in rules always win, and `gl_torch_dlight 0` still switches the whole group off (requested by Mathuzzz)
  - `mcache` now reports which lighting group the engine assigned each model, so a mistyped name is distinguishable from a light being suppressed elsewhere
- Added `r_water_pixel_warp` cvar (default: 0), evaluating the liquid warp per pixel rather than per vertex. The classic warp samples a sine at surface-subdivision corners and lets the rasteriser join the dots, which at the shipped subdivision size overshoots the intended ripple by 165% and turns a 50-unit undulation into a 234-unit one; no affordable subdivision size fixes it. The per-pixel path has no such error, and its amplitude is scaled by the closed-form average of the sine over each pixel's footprint, so distant water fades to flat instead of aliasing. Off by default pending visual sign-off

❗ **Note**: `sv_physfps` changes how fast the world runs, so anything you had tuned around the old 20 Hz — a mod, a demo, a speedrun route — will behave differently. Setting `sv_physfps 20` reproduces r15 exactly.

### Downloads

- **Linux x86_64** — extract and run `glhexen2` from your Hexen II data directory
- **Linux Flatpak** — `flatpak install hexenwail-*.flatpak`, then place game data in `~/.var/app/io.github.hexenwail.hexenwail/.hexen2/data1/`
- **Windows x86_64** — extract anywhere, drop `pak0.pak`/`pak1.pak` into the included `data1/` folder, run `glh2.exe`

Requires game data files (`data1/pak0.pak`, `data1/pak1.pak`).

### Compiled gamecode — included, and already in use

Both zips carry the Hexen II game logic rebuilt from source, with fixes that are
not in Raven's 1997 `progs.dat` (chiefly dropped backpacks silently vanishing in
co-op and deathmatch).

**There is nothing to install.** The engine ships its own copy beside the
executable and prefers it to the one in your Hexen II folder — on Linux and on
Windows alike, straight out of the zip. Nothing is copied and nothing of yours is
overwritten.

- **To see which gamecode you are running**, look for the `Gamecode:` line the
  engine prints when it loads one. It names the exact file and its checksum.
- **To turn it off**, launch with `-vanillaprogs`. The engine then ignores its own
  copy and uses whatever your Hexen II install provides. Nothing is deleted, so it
  is a per-launch decision.
- **To run different gamecode** — a translation, a balance patch, your own build —
  put it in `~/.hexen2/<gamedir>/` on Linux, which outranks the bundled copy.
  Windows has no user directory, so replace the files in `gamecode/` beside
  `glh2.exe` instead.

The `gamecode/` folder in the zip is those same three files. On Windows it *is*
the copy the engine loads, since it sits next to `glh2.exe`; on Linux the engine
loads its own from the platform directory and this one is a spare you can install
by hand into a different engine. See `gamecode/README.txt`.

Two things to know:

- **"Vanilla" now means two different things.** A build running our gamecode will
  behave differently from Raven's in ways that are not engine bugs. If you report
  a problem, please paste the `Gamecode:` line, or say whether `-vanillaprogs`
  changes what you see — that is the fastest way to tell whose bug it is, and it
  deletes nothing. This cuts both ways — some reports against older releases will
  have been gamecode issues we had already fixed.
- **Portals: the Crusader's Glyph of the Ancients damages you too.** The glyph
  detonates on whoever touches it for real damage — 50 in deathmatch, 37
  otherwise — the caster included. Do not walk into your own glyph. This is
  Raven's original behaviour, so nothing changes if you are coming from a stock
  `progs.dat`; it is called out because Hexenwail's own gamecode briefly let the
  glyph pass harmlessly through the caster, and that exemption is gone.

### Reporting a crash

Windows builds report crashes by themselves — there is nothing to install or enable.
If the game dies, a file called `glh2.RPT` appears next to `glh2.exe`.
Attach that file and `qconsole.log` from the same folder to your report.

The Windows build ships with debug symbols, so that report names the source file
and line the game died on — there is no separate debug download to fetch.

To verify a download, fetch `SHA256SUMS` alongside it and run `sha256sum -c SHA256SUMS`.
