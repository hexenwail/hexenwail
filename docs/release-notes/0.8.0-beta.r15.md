### Changes from [0.8.0-beta.r14](https://github.com/hexenwail/hexenwail/releases/tag/0.8.0-beta.r14)

A field-report release: everything below came from one round of testing by Mathuzzz.

- Fixed monsters and player models animating in steps instead of blending. A model whose frames deform a lot between poses is meant to skip interpolation — flames and torches, whose "frames" are unrelated artwork — but the check was also measuring the seam between the end of one animation and the start of the next, poses nothing ever blends. One such seam was enough to switch interpolation off for every animation that model had. Twelve of the game's models were affected, the Archer and four of the five player classes among them
- Fixed translucent models drawing as hard opaque shapes when a texture pack replaces their skin. A model marked as having cut-out holes was always treated as a hard-edged cut-out, but a replacement skin can carry a genuine transparency gradient instead — Shadows of Turmoil's drifting mist does, and was losing 95% of itself and drawing the rest solid. Such skins now blend as their author intended, and no longer clip each other where several overlap
- Fixed the console not closing on keyboard layouts where the console key is not `` ` `` or `~`. Any key bound to `toggleconsole` now toggles both ways instead of opening the console and then typing itself into it. Gamepad **Back** works from menus for the same reason
- Fixed a roughly 25-second freeze, ending in `load timeout.`, when `map` is given a map the current mod does not have — for instance a Shadows of Turmoil level from the base game. The error was being printed to a console the engine had stopped drawing. It now reports immediately and leaves the console usable
- Fixed the console being unreachable from the menu after that error, which needed a level to be started before it came back
- Added `screenshot [png|tga|jpg] [quality]`, defaulting to PNG, matching Ironwail's per-invocation choice rather than a cvar. The bundled `stb_image_write` had been trimmed to the JPEG encoder only, so nothing in the engine could write a compressed image
- Added mapper control over how far a `misc_modelpimp`'s effects reach. Its glow and cast-light have always been applied to every model on the map sharing that model, while spin and float stayed on the controller alone; that split is right for mods that light a whole set of props from one hidden entity and backwards for anyone wanting a single glowing prop. All three new spawnflags are off by default, so existing maps are unchanged:
  - **16 — Self only**: keep the glow and cast-light on this entity instead of sharing them
  - **32 — Share motion**: give sibling models the spin and float as well
  - **64 — No dynamic light**: cast no dynamic light at all, leaving the baked lighting to carry it. Hexen II's dynamic lights do not test for walls, so a light near one spills through; this is the lever to take a specific one out until the engine can cast shadows

❗ **Note**: weapons that a mod flags as transparent — the Cleric's raven staff in Shadows of Turmoil among them — still draw opaque. That is unchanged from r14 and is tracked separately; it is not affected by the model transparency fix above, which applies to world models.

### Downloads

- **Linux x86_64** — extract and run `glhexen2` from your Hexen II data directory
- **Linux Flatpak** — `flatpak install hexenwail-*.flatpak`, then place game data in `~/.var/app/io.github.hexenwail.hexenwail/.hexen2/data1/`
- **Windows x86_64** — extract anywhere, drop `pak0.pak`/`pak1.pak` into the included `data1/` folder, run `glh2.exe`

Requires game data files (`data1/pak0.pak`, `data1/pak1.pak`).

### Compiled gamecode — included, and already in use

Both zips carry the Hexen II game logic rebuilt from source, with fixes that are
not in Raven's 1997 `progs.dat` (chiefly dropped backpacks silently vanishing in
co-op and deathmatch).

**There is nothing to install.** The engine ships its own copy beside the
executable and prefers it to the one in your Hexen II folder — on Linux and on
Windows alike, straight out of the zip. Nothing is copied and nothing of yours is
overwritten.

- **To see which gamecode you are running**, look for the `Gamecode:` line the
  engine prints when it loads one. It names the exact file and its checksum.
- **To turn it off**, launch with `-vanillaprogs`. The engine then ignores its own
  copy and uses whatever your Hexen II install provides. Nothing is deleted, so it
  is a per-launch decision.
- **To run different gamecode** — a translation, a balance patch, your own build —
  put it in `~/.hexen2/<gamedir>/` on Linux, which outranks the bundled copy.
  Windows has no user directory, so replace the files in `gamecode/` beside
  `glh2.exe` instead.

The `gamecode/` folder in the zip is those same three files. On Windows it *is*
the copy the engine loads, since it sits next to `glh2.exe`; on Linux the engine
loads its own from the platform directory and this one is a spare you can install
by hand into a different engine. See `gamecode/README.txt`.

Two things to know:

- **"Vanilla" now means two different things.** A build running our gamecode will
  behave differently from Raven's in ways that are not engine bugs. If you report
  a problem, please paste the `Gamecode:` line, or say whether `-vanillaprogs`
  changes what you see — that is the fastest way to tell whose bug it is, and it
  deletes nothing. This cuts both ways — some reports against older releases will
  have been gamecode issues we had already fixed.
- **Portals: the Crusader's Glyph of the Ancients damages you too.** The glyph
  detonates on whoever touches it for real damage — 50 in deathmatch, 37
  otherwise — the caster included. Do not walk into your own glyph. This is
  Raven's original behaviour, so nothing changes if you are coming from a stock
  `progs.dat`; it is called out because Hexenwail's own gamecode briefly let the
  glyph pass harmlessly through the caster, and that exemption is gone.

### Reporting a crash

Windows builds report crashes by themselves — there is nothing to install or enable.
If the game dies, a file called `glh2.RPT` appears next to `glh2.exe`.
Attach that file and `qconsole.log` from the same folder to your report.

The Windows build ships with debug symbols, so that report names the source file
and line the game died on — there is no separate debug download to fetch.

To verify a download, fetch `SHA256SUMS` alongside it and run `sha256sum -c SHA256SUMS`.
