**Parity: ~81% ported (91/113), 1% partial, 19% missing** (excluding N/A).  Recounted 2026-09-01 by `tools/ironwail_scorecard.py`, which is the hand-rolled parser described below, now committed so the next edit cannot skip it — it reproduced the 2026-08-31 figures for every other section before being trusted with this one, and on its first real use caught Debug / Tooling reading 1/0/3/0 against an actual 3/0/1/0 (the `r_showfields` row had shipped and never been moved).  Previously recounted 2026-08-31 after the first *structural* audit this document has had — and recounted **mechanically**, by parsing the status column out of every table row, not by hand.  The first draft of this very table was written by hand and came out 87 / 2 / 20 / 9 against an actual 87 / 1 / 24 / 9; the script that caught it is the same discipline the 2026-08-20 entry adopted after the table drifted to 85 / 2 / 1 / 9.  Hand-summarising a table you just edited does not work, twice demonstrated.

The previous figure of ~99% (87/88) was not bad arithmetic — it was the right arithmetic over the wrong denominator.  Every audit before this one worked by diffing Ironwail's **commit log** against what we had ported, so the tables only ever grew rows for features Ironwail *changed* during the compared window.  Anything Ironwail had already built before we started looking was invisible to the method, and stayed invisible no matter how carefully the window was re-walked.  Clustered dynamic lighting and lit water are both in that category: neither is new upstream work, both are years old, and neither had a row here.

This pass diffed **inventories** instead — every `cvar_t` declaration, every `Cmd_AddCommand`, and the `glprogs_t` shader-program struct — which finds gaps regardless of when upstream introduced them.  86 Ironwail cvars had no name-match here, and 83 of those appear nowhere in `engine/` under any spelling; 40 commands likewise.  Both raw figures overstate the gap before renames (`vid_config_*` for `vid_*`, `showfps` for `scr_showfps`) and genuinely Quake-only items (`campaign`, `horde`, `language`, `scr_usekfont`) are subtracted — the per-row triage below is what the scorecard counts, not these totals.

**The lesson is the same one this document recorded on 2026-08-22 and did not generalise far enough.**  That entry noted a row can cite the code correctly and still record a defect, because "what the engine does" and "what the engine should do" are different claims.  The 2026-08-31 finding is the next step out: a *table* can be individually accurate in every row and still misreport parity, because "what we have compared" and "what exists to compare" are also different claims.  A tracker that only ever grows rows from a diff can never report a gap the diff cannot see.  Row-level accuracy was never the binding constraint; coverage was.

The one ❌ that survives from the old count is bindless textures, and it remains a **decision, not a backlog item** — reclassified out of ➖ N/A on 2026-08-18 once Ironwail was actually checked, then declined on measured grounds on 2026-08-20 (uhexen2-im9g closed).  It stays ❌ rather than ➖ precisely because a gap declined on measured grounds is still a gap.

| Bindless textures | ❌ | **Reclassified ➖ N/A → ❌ Missing on 2026-08-18.**  Every prior revision of this row asserted "Ironwail does not use `ARB_bindless_texture` either".  That is false.  Ironwail has a live, working bindless path: `gl_bindless_able` is set in `gl_vidsdl.c` behind `GL_FindExtension("GL_ARB_bindless_texture") && GL_InitFunctions(...)`, textures carry `TEXPREF_BINDLESS`, `gl_texmgr.c` calls `GL_GetTextureSamplerHandleARB` / `MakeTextureHandleResident`, the shaders compile with `#define BINDLESS %d` and real `#if BINDLESS` branches, and `r_world.c` uses it on the world draw path — which is exactly the batched use case.  So this is a genuine parity gap, not a Quake-specific irrelevance.  Our own scaffolding was still correctly **removed** in `bbf4a97a5` (uhexen2-ubsu): its ARB entry points were declared through `GL_FUNCTION_OPT`, which `GL_Init_Functions` expands to nothing, so `gl_bindless_able` could never be true and every downstream defect sat behind a gate wired shut.  Removing dead code was right; calling the feature N/A was not.  (Revisions of this row and the shortlist before 2026-08-20 cited `8124ed055` for that removal; an interactive rebase had replaced it with `bbf4a97a5`.)  **Declined on measured grounds 2026-08-20 — uhexen2-im9g closed.**  Its own gate was "show that per-draw texture binding is actually a dominant bucket".  It is not, and the ceiling is a property of the content rather than of any GPU: `DrawTextureChains` issues one `GL_Bind` per texture chain with visible surfaces, so the distinct textures a map's faces reference bound the world pass.  Across all 59 shipped maps in `data1`, `portals`, `sot`, `soc`, `karma2` and `GameOfTomes` that ceiling is **119** (`village2.bsp`), mean 58 — reproduce with `tools/bsp_texcount.py`.  `gl_lmatlas` defaults to 1 so the lightmap is one atlas bind per frame, and the alias path already binds per batch (`GL_Bind(batch->skin_tex)`), not per entity.  A few hundred binds per frame cannot dominate a 16.7 ms budget.  The one place binds genuinely multiply is the bmodel walk, which flushes on texture *change* while iterating in surface order and so re-binds the same texture repeatedly — that is a sorting defect whose fix is to sort, not to take an extension dependency.  `c_texbinds` is on `r_speeds 2` if anyone wants to falsify this from inside a frame.  **Corroborated independently 2026-08-20**: asked about it on Discord, Spoike (FTE) went straight to the portability cost — "good luck with that, if you value web/wasm compat".  `ARB_bindless_texture` has no WebGL2 equivalent, so the bindless path would have to be a second world-draw path maintained alongside the `#version 300 es` one our web build already needs.  That is a cost the measurement above says buys nothing. |

| MD5mesh / IQM skeletal model support | ✅ | Completed 2026-08-20 (uhexen2-7ok0).  Phase 1 (2026-06-12) made the parser crash-safe.  Phases 2 and 3 added the `.md5anim` parser — token scanner, hierarchy/bounds/baseframe/frame blocks, per-joint animated-channel masks composed parent-before-child, each stored bone matrix being `anim_world × inv_rest_world` so it maps a vertex from its rest world position to its animated one and cancels to identity at rest — and the `PV_IQM` draw dispatch (`GL_DrawAliasSkeletal`), which binds the bone SSBO and finally invokes `gl_shader_skeletal`.  One MD5 frame maps to one `aliashdr_t` frame so `e->frame` indexes it like a `.mdl` and `R_AliasResolveLerp` applies unchanged; the shader takes two pose bases and blends, so MD5 models lerp like every other alias model.  Its normal-as-colour debug output was replaced with the same `1.0 + dot(normal, shadevector)` the shadedots table encodes.  Also: skin loading from the mesh's `shader` string, and culling bounds unioned with the anim's per-frame bounds.  Testing found three latent parser bugs phase 1's crash-safety review missed — `strstr(p,"vert")` matched inside `numverts` (likewise `tri`/`weight`), weight binning assumed vertex-major file order, and `hdr->scale` was left at the zero memset default while the draw path multiplies by it.  Synthetic test models in `engine/tests/md5/`.  Still no `.iqm` parser — `iqmvert_t` is an internal vertex struct name, and Ironwail's rerelease models are MD5, so IQM is not a parity gap.  Real-asset visual verification (triangle winding) tracked as uhexen2-2t38. |

| Clustered GPU dynamic lighting | ❌ | **Added 2026-08-31 — this document had no row for it at all.**  Ironwail evaluates dynamic lights per-pixel from a froxel grid; we run the QuakeSpasm path it replaced.  Upstream: `LIGHT_TILES_X 32` / `LIGHT_TILES_Y 16` / `LIGHT_TILES_Z 32` (`glquake.h`), Z sliced logarithmically via `r_framedata.zlogscale = LIGHT_TILES_Z / (logzfar - logznear)` (`gl_rmain.c`), a `cluster_lights` compute program built in `gl_shaders.c` as `GL_CreateComputeProgram (cluster_lights_compute_shader, "light cluster")`, and a `gpulightbuffer_t` SSBO holding `float lightstyles[MAX_LIGHTSTYLES]` next to `gpulight_t lights[MAX_DLIGHTS]` — `gpulight_t` being `{ pos[3], radius, color[3], minlight }`.  No lightmap is rebuilt for a dlight.  Ours: `R_MarkLights` recursing the BSP marking `surf->dlightframe` (`gl_rlight.c`), `R_AddDynamicLights` accumulating into the CPU lightmap block from `R_BuildLightMap` (`gl_rsurf.c`), and `lightmap_modified[MAX_LIGHTMAPS]` driving a per-frame re-upload of every dirtied page.  **This is the largest single pipeline difference between the two engines**, and it is why our lightmap atlas cannot live in immutable storage.  Hexen II leans on dlights hard — torches, missiles, spell effects — so the ceiling is reached in ordinary play.  Sequence it before uhexen2-i0tr (shadow-casting dlights), which wants a GPU-side light representation to build on.  uhexen2-a5nn.1. |

## Performance / Engine

| Feature | Status | Notes |
|---|---|---|
| Reduced heap usage / auto-grow | ✅ | Large maps load without `-heapsize` |
| Visible-entity cap (MAX_VISEDICTS) | ✅ | Bumped 256 → 16384 in `client.h` to match Ironwail.  At 256, dense maps silently dropped entities past the cap; manifested as multi-reporter "models and brush ents pop at distance" (uhexen2-l0ac). | Per-entity leaf cap (MAX_ENT_LEAFS) | ✅ | **Now beyond Ironwail.** History is 16 (vanilla) → 32 (ericw / QuakeSpasm / Ironwail, where it still sits) → **64** here, bumped in `32c35acdb` after Keep.bsp re-reported popping at 32 (uhexen2-l0ac). `SV_WriteEntitiesToClient` also skips the PVS cull when an entity hits the cap, so it is always sent — that always-send path stays as the safety net for the absurd cases. Long brush ents (lifts, rotators) that touched more than 16 BSP leaves had their leaf list truncated, and the PVS cull then dropped them from the client write stream as the player moved. Cost is 256 B per edict over the 32 baseline. |

| Entity update priority sort (`sv_netsort`) | ❌ | **Added 2026-08-31.**  Ironwail sorts entities by a distance/size key before writing them into the client datagram, so when the packet fills, what gets dropped is far-away and small rather than whatever came last in edict order.  `SV_WriteEntitiesToClient` (`sv_main.c`): the client entity is pinned to bin 0 at distance 0, then per entity `dist` accumulates `CLAMP (absmin[i], org[i], absmax[i]) - org[i]` squared while `size` accumulates the bbox extent squared, and the sort key is `8.f * sqrt (sqrt (dist/size))` clamped to 255. ### Resolved — bindless textures (was P1)
1. **Bindless textures** — ❌ genuine parity gap, **declined 2026-08-20** (uhexen2-im9g closed).
