The previous figure of ~99% (87/88) was not bad arithmetic — it was the right arithmetic over the wrong denominator.  Every audit before this one worked by diffing Ironwail's **commit log** against what we had ported, so the tables only ever grew rows for features Ironwail *changed* during the compared window.  Anything Ironwail had already built before we started looking was invisible to the method, and stayed invisible no matter how carefully the window was re-walked. This pass diffed **inventories** instead — every `cvar_t` declaration, every `Cmd_AddCommand`, and the `glprogs_t` shader-program struct — which finds gaps regardless of when upstream introduced them.  86 Ironwail cvars had no name-match here, and 83 of those appear nowhere in `engine/` under any spelling; 40 commands likewise. **The lesson is the same one this document recorded on 2026-08-22 and did not generalise far enough.**  That entry noted a row can cite the code correctly and still record a defect, because "what the engine does" and "what the engine should do" are different claims.  The 2026-08-31 finding is the next step out: a *table* can be individually accurate in every row and still misreport parity, because "what we have compared" and "what exists to compare" are also different claims.  A tracker that only ever grows rows from a diff can never report a gap the diff cannot see.  Row-level accuracy was never the binding constraint; coverage was.

The one ❌ that survives from the old count is bindless textures, and it remains a **decision, not a backlog item** — reclassified out of ➖ N/A on 2026-08-18 once Ironwail was actually checked, then declined on measured grounds on 2026-08-20 (uhexen2-im9g closed).  It stays ❌ rather than ➖ precisely because a gap declined on measured grounds is still a gap.

| Bindless textures | ❌ | **Reclassified ➖ N/A → ❌ Missing on 2026-08-18.**  Every prior revision of this row asserted "Ironwail does not use `ARB_bindless_texture` either".  That is false.  Ironwail has a live, working bindless path: `gl_bindless_able` is set in `gl_vidsdl.c` behind `GL_FindExtension("GL_ARB_bindless_texture") && GL_InitFunctions(...)`, textures carry `TEXPREF_BINDLESS`, `gl_texmgr.c` calls `GL_GetTextureSamplerHandleARB` / `MakeTextureHandleResident`, the shaders compile with `#define BINDLESS %d` and real `#if BINDLESS` branches, and `r_world.c` uses it on the world draw path — which is exactly the batched use case.  So this is a genuine parity gap, not a Quake-specific irrelevance.  Our own scaffolding was still correctly **removed** in `bbf4a97a5` (uhexen2-ubsu): its ARB entry points were declared through `GL_FUNCTION_OPT`, which `GL_Init_Functions` expands to nothing, so `gl_bindless_able` could never be true and every downstream defect sat behind a gate wired shut.  Removing dead code was right; calling the feature N/A was not.  (Revisions of this row and the shortlist before 2026-08-20 cited `8124ed055` for that removal; an interactive rebase had replaced it with `bbf4a97a5`.)  **Declined on measured grounds 2026-08-20 — uhexen2-im9g closed.**  Its own gate was "show that per-draw texture binding is actually a dominant bucket".  It is not, and the ceiling is a property of the content rather than of any GPU: `DrawTextureChains` issues one `GL_Bind` per texture chain with visible surfaces, so the distinct textures a map's faces reference bound the world pass.  Across all 59 shipped maps in `data1`, `portals`, `sot`, `soc`, `karma2` and `GameOfTomes` that ceiling is **119** (`village2.bsp`), mean 58 — reproduce with `tools/bsp_texcount.py`.  `gl_lmatlas` defaults to 1 so the lightmap is one atlas bind per frame, and the alias path already binds per batch (`GL_Bind(batch->skin_tex)`), not per entity.  A few hundred binds per frame cannot dominate a 16.7 ms budget.  The one place binds genuinely multiply is the bmodel walk, which flushes on texture *change* while iterating in surface order and so re-binds the same texture repeatedly — that is a sorting defect whose fix is to sort, not to take an extension dependency.  `c_texbinds` is on `r_speeds 2` if anyone wants to falsify this from inside a frame.  **Corroborated independently 2026-08-20**: asked about it on Discord, Spoike (FTE) went straight to the portability cost — "good luck with that, if you value web/wasm compat".  `ARB_bindless_texture` has no WebGL2 equivalent, so the bindless path would have to be a second world-draw path maintained alongside the `#version 300 es` one our web build already needs.  That is a cost the measurement above says buys nothing. |

| MD5mesh / IQM skeletal model support | ✅ | Completed 2026-08-20 (uhexen2-7ok0).  Phase 1 (2026-06-12) made the parser crash-safe. One MD5 frame maps to one `aliashdr_t` frame so `e->frame` indexes it like a `.mdl` and `R_AliasResolveLerp` applies unchanged; the shader takes two pose bases and blends, so MD5 models lerp like every other alias model.  Its normal-as-colour debug output was replaced with the same `1.0 + dot(normal, shadevector)` the shadedots table encodes. | Clustered GPU dynamic lighting | 🔶 | **Done 2026-09-01 (uhexen2-a5nn.1 phases A+B+C); the alias half goes past upstream.**  `gl_lightcluster.c` builds Ironwail's froxel grid — `LIGHT_TILES_X 32` / `_Y 16` / `_Z 32`, logarithmic Z slices, a `cluster_lights` compute program, and a `gpulightbuffer_t`-shaped SSBO holding `float lightstyles[MAX_LIGHTSTYLES]` next to `gpulight_t {pos[3], radius, color[3], minlight}` — and `GLSL_DLIGHT_FN` in `gl_shader.c` shades every world fragment from it.  `R_PushDlights` and both brush-entity marking loops stand down while it is on, so **no lightmap page is re-uploaded for a dynamic light**: measured 0 pages / 0 rebuilds per frame against 2 pages / 46 rebuilds on the CPU path, in a torch-lit corridor on demo1.  THREE THINGS THIS IS NOT.  (a) It is not a replacement: the ES/WebGL2 tier has neither compute nor SSBOs, so `R_AddDynamicLights` stays live there forever and the desktop path is gated on `r_lightclusters` (default 1) plus `gl_renderer_caps`.  (b) It is not pixel-identical to the path it replaces, and should not be — the CPU measures dlight falloff in TEXTURE units (`DotProduct(impact, tex->vecs[i])`), so a light's size there scales with the surface's texture scale; on demo1's corridor floor (`|vecs|` 0.6667, scale 1.5) the CPU pool is half again too wide.  The GPU uses world distance, as Ironwail does, so dynamic lights visibly tighten on scaled-texture surfaces.  (c) Alias models followed in phase C, and that half is **not an Ironwail port** — upstream's alias shader reads no froxel list at all and its models keep the CPU term (`Quake/gl_shaders.h` `alias_vertex_shader`, `Quake/r_alias.c:295`), as does the Hexen II reference fork.  Ours evaluates the same `radius - distance` expression per pixel instead of once at the entity origin, behind its own `r_lightclusters_models` (default 1) so the two changes A/B apart; `r_lightclusters_models 0` is the way back to upstream's behaviour.  Deliberately NOT a reuse of the world path's `ClusteredDlight`: that one's falloff is `R_AddDynamicLights`' surface-plane approximation and its normal comes from screen-space derivatives, which is exact only because BSP faces are planar — on an alias model it would yield the flat triangle normal and break the light into facets.  The dlight is also no longer modulated by the shadedots table or the colorshade tint, because the legacy path streams a finished vertex colour with both already multiplied in and having the three alias paths disagree is worse than either choice.  Measured on a frozen demo1 frame with one stationary light: toggling the cvar off and back on is pixel-identical (0 differing pixels), the on-vs-off difference falls entirely inside model silhouettes, and the instanced and legacy paths agree to 0.07 px.  Ours also carries Hexen II's subtractive `dark` lights, which Quake has no equivalent of, as a negated colour accumulated with a clamp at zero.  uhexen2-26bm, uhexen2-waum. |

| Enhanced model substitution (`r_enhancedmodels`) | ✅ | **Added and done 2026-09-01** (uhexen2-a5nn.6).  `r_enhancedmodels` (1) and `r_enhancedmodels_priority` ("md3,md5"), archived, with Ironwail's change callback so a toggle re-resolves what is already loaded instead of waiting for the next map. ### Resolved — bindless textures (was P1)
1. **Bindless textures** — ❌ genuine parity gap, **declined 2026-08-20** (uhexen2-im9g closed).
